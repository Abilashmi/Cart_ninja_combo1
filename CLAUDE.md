## Architecture Overview

This is a **Shopify embedded app** built with React Router v7, Polaris UI, and a dual-database setup. It provides cart drawer customization, upsell/FBT widgets, coupon sliders, and a bundle builder (Combo Forge).

### Dual Database Pattern

The app writes to **two separate databases simultaneously**:

1. **MySQL** (`cart_drawer_ninja`) via `app/services/db.server.js` — the production store. Direct `mysql2/promise` pool. Used for all normalized widget settings tables (`cart_drawer_config`, `progress_bar_settings`, `coupon_slider_settings`, `upsell_widget_settings`, `fbt_widget_settings`, etc.).

2. **SQLite via Prisma** (`prisma/schema.prisma`) — used for Shopify session storage, `combo_templates`, `combo_analytics`, `upsell_rules`, and Shopify-facing models. Connection via `app/db.server.js` (exports default Prisma client).

3. **PHP backend** at `https://int.thecomboforge.com` — a separate server handling legacy templates, discounts, analytics, and the `cart_drawer` table. Accessed through `app/utils/api-helpers.js` (`getDb`, `sendToPhp`). The `cart_drawer` table (MySQL, legacy) is distinct from `cart_drawer_config` (newer normalized table).

When adding new fields, you typically need:
- An `ALTER TABLE` on MySQL (via the PHP backend or direct query)
- An upsert update in the relevant `api.*` route
- State wired in `CartEditorContext` and `cartEditorTypes.js`

### AI API Key Convention

All AI routes use `process.env.OPENAI_API_KEY` to hold the **NVIDIA NIM key** (`nvapi-...`). The key's prefix determines the endpoint and model:
- `nvapi-*` → `https://integrate.api.nvidia.com/v1/chat/completions` + `meta/llama-3.1-8b-instruct`
- Anything else → `https://api.openai.com/v1/chat/completions` + `gpt-4o-mini`

This detection pattern must be applied in both Node.js routes and PHP files (`php_backend/ai_upsell.php` already patched).

### BrixBar — the one AI system

There is a **single** AI UI in this app: **BrixBar** (`app/components/ai-agent/BrixBar.jsx`), an inline prompt bar mounted directly in page JSX across most `/app/*` pages (`app.cartdrawer` via `CartEditorSidebar.jsx`, `app.bundles.customize.jsx`, `app.bundles._index.jsx`, `app.productwidget.jsx`, `app.additional.jsx`, `app.coupons.jsx`, `app.analytics.jsx`, `app.fbt.jsx`). A prior "CartNinja" floating-chat system has been fully removed — if you see it mentioned in old comments/memory, it's stale.

`BrixBar` must be mounted **once per page** — `app.bundles.customize.jsx` has historically had duplicate `<BrixBar />` instances that cause double-UI bugs. Always check for this when editing that file.

### Cart Editor (app/routes/app.cartdrawer.jsx)

The cart editor is a live-preview builder split into:

- **`CartEditorContext`** (`app/context/CartEditorContext.jsx`) — single source of truth for all editor state. Exposes `updateGeneral`, `updateDesign`, `updateHeader`, `updateAnnouncements`, `updateEmptyCart`, `updateCountdownTimer`, etc.
- **`CartEditorSidebar`** → renders section panels from `app/components/sections/`. Each section component pulls state from context. Sections: `design`, `general`, `header`, `announcements`, `progressBar`, `couponSlider`, `upsellProducts`, `countdownTimer`, `emptyCart`, `checkoutButton`, `customCSS`.
- **`CartPreview`** — right-side live preview, also reads from context.
- **Save flow** (`CartEditorPage.handleSave`): fires two parallel saves — a legacy blob to `POST /app/cartdrawer` and normalized saves to `/api/cart-drawer-config`, `/api/progress-bar`, `/api/coupon-slider-settings`, `/api/upsell-settings`, `/api/countdown-timer`.
- **Save layer** (`app/services/cart-config-writes.server.js`): every normalized route above is a thin wrapper around a shared save function here (`saveCartDrawerConfig`, `saveProgressBarSettings`, `saveUpsellWidgetSettings`, `saveCouponSliderSettings`, `saveFbtWidgetSettings`, `saveCountdownTimerSettings`). Each fetches the existing row first and merges — a field omitted from the caller's patch falls back to the current DB value, never a hardcoded default — so the AI agent's tool calls (which often touch one field at a time) can never silently reset unrelated fields. The AI tool executors (`ai-agent-tools.server.js`) call these same functions directly, in-process.

The `cart_drawer_config` MySQL table is the canonical store for announcement, general, header, design, empty cart, and countdown timer fields (the newer normalized path) — and is what the storefront reads live via a `LEFT JOIN` in `save_cart_drawer.php`'s GET handler for header/announcement/design/empty-cart fields. The legacy `cart_drawer` table (on the PHP backend MySQL) still owns `cartStatus` (drawer on/off), `checkout_button_style` (JSON blob — the storefront's *only* source for checkout button styling; `cart_drawer_config`'s `checkout_button_*` columns are admin-preview-only), and `custom_css`/`countdown_data` blobs. Any code path that changes checkout-button appearance or drawer on/off state must write **both** tables, or the change won't reach the storefront — see `ai-agent-tools.server.js`'s `syncCheckoutButtonToLegacyRecord`/`syncDrawerStatusToLegacyRecord` helpers (the manual editor's own `CartEditorPage.handleSave` already does this via its parallel legacy-blob POST).

Default state shape lives in `app/types/cartEditorTypes.js` (`defaultCartEditorState`).

**Checkout button size.** Cart Editor → Checkout Button has Text size (`fontSize`, 12-22, default 15) and Button height (`paddingY`, 8-28, default 16), stored only in the legacy `cart_drawer.checkout_button_style` JSON (the storefront's source; no new columns). `cart_drawer_inline.js` `parseCheckoutButtonStyle` clamps them and every button mode uses them (swipe track height = 20 + 2 × paddingY); `CartPreview.jsx` draws them at the preview's 13/15 and 11/16 scale. The drawer's COD button has its own padding: `settings.buttons.paddingY / paddingX` (COD → Customize → Cart drawer button → Button size; `COD_BUTTON_PADDING`, re-checked in `cod_storefront.php` `cods_button_look`, used by `brix_cod.js` `drawerSize`).

**Shared drawer UI (rows, pricing, banner).** Cart item rows (`.bxcd-item`), the pricing summary (`.bxcd-summary`) and the Cart Image Banner use one stylesheet, `extensions/cart-drawer/assets/brix_cart_ui.css`, loaded by the app embed and, in the admin, `<link>`ed by `CartPreview.jsx` from the app route `/brix_cart_ui.css` (`routes/brix_cart_ui[.]css.jsx`) — never `import` a file from `extensions/` into client code: in `shopify app dev` the CLI proxy answers every `/extensions/...` URL with a 404, the route module fails to load, and the page renders from the server but nothing is clickable; the storefront builds the markup in `cart_drawer_inline.js` (`renderCartItemHtml`, `renderSummaryHtml`, `renderBannerHtml`) and `PreviewCartItems.jsx` mirrors it. Mobile layout = storefront below 480px, preview's phone frame (`.bxcd-root--mobile`); the storefront's tighter phone spacing (header, body, progress/coupon sections, footer) is the `@media (max-width: 480px)` block in `cart_drawer_inline.css`, overriding inline styles with `!important`. The footer (summary + checkout + COD slot) renders only when `cart.items.length > 0` (`hasCartItems`); an empty cart gets the empty state and no checkout, in preview and storefront.

**Cart Image Banner** (`body.imageBanner`, sidebar section "Image Banner"): `banner_enabled / banner_desktop_image / banner_mobile_image / banner_placement / banner_alt / banner_margin_top / banner_margin_bottom` (px, 0-40, default 12; the banner's margin replaces the body's `--cc-gap` section gap) on `cart_drawer_config` (self-healing columns in `cart-config-writes.server.js` and `save_cart_drawer.php`; `migrations/add_cart_drawer_image_banner_fields.sql` for reference). Images are https links or browser-compressed data URLs (`BannerImageField.jsx`, no `write_files` scope); the storefront GET never sends the data, only `banner_*_src` links to `php_backend/cart_banner_image.php` (year-long cache, versioned by hash) and uses `<picture>` so one image loads. Placement rules (`app/utils/cart-banner.shared.js` `bannerSlot`, mirrored by `ccBannerSlot`): Above/Below Progress Bar follow the bar (top of body with no bar), Above/Below Products, Above Checkout (end of body); on the storefront each slot is a CSS `order` value (progress bar -20/980, coupons -10/990). BRIX sets it with the `update_image_banner` tool (on/off, https image links, placement, alt; asks for an image link when switched on without one); `get_current_config` replaces stored images with `'uploaded image'` so data URLs never reach the model. Tests: `tests/cart-drawer/` (unit, PHP harness end to end, storefront + editor browser checks).

**Coupons: shared settings row and text offers.** `coupon_slider_settings` is shared by the Cart Editor's coupon section and the Coupon Banner page (`app.productwidget.jsx`). The Coupon Banner saves only its own fields (on/off, template, placement, layout) through the merge-safe `saveCouponSliderSettings` (the old PHP `coupon_slider_settings.php` POST rewrote every column and reset the drawer's title and coupon cards), and the Cart Editor hydrates its coupon section from the drawer's own `cart_drawer.coupon_data` first (what the storefront drawer reads), using the shared row only for fields that blob lacks. Banner icon default: shown on Bold & Vibrant (replaces the old 🏷️ emoji), hidden on the other two unless switched on. Tests: `tests/coupon-banner/{admin,storefront}-browser-check.mjs`, coupon parts of `tests/cart-drawer/{editor-preview,drawer-ui}-browser-check.mjs`.

**Upsell products and stock.** The drawer reads each product from `/products.json` through `ccProductDetail` (also used for Shopify recommendations, prices in paise there): `variantId` is the first **in-stock** variant (never blindly `variants[0]`, which is often a sold-out size; free reward products use it too), and `variants` feeds a dropdown on every upsell card style (`ccUpsellVariantSelect`, sold-out options listed but disabled; changing it updates price, image and the Add button). Products past the first 250 are found by paging (`ccEnsureCatalogProducts`, up to 8 pages). A fully sold-out pick follows `upsell_data.soldOutBehavior`: `replace` (default) fills its spot from Shopify's `/recommendations/products.json?intent=related` (in stock, not in the cart; related to the sold-out product first, then the cart's items), `hide` just drops it; the card count stays the merchant's number of picks (AI mode: the limit). A 422 on Add shows "Sold out", disables that option and moves to the next in-stock one. Admin: Upsell section "When a product is sold out"; the preview (`CartPreview.jsx` `UpsellVariantSelect`) mirrors the dropdown and uses other in-stock store products as stand-ins (it can't call Shopify recommendations). Tests: `node tests/cart-drawer/upsell-stock-browser-check.mjs`, upsell part of `editor-preview-browser-check.mjs`.

**Colour inputs.** Every admin colour field is `components/shared/ColorField.jsx` (`sections/ColorField.jsx` re-exports it): hex text box + swatch picker, synced both ways; a typed code is saved only once valid (`#rgb`/`#rrggbb`, stored as `#rrggbb`, rules in `utils/color.shared.js`), else an inline error; `allowEmpty` + `fallback` = "empty means use the default". **Pairing Assistant (FBT + cart upsells).** FBT → Configure → Manual ("Describe in words" / "From past orders" next to "Pick products") and the Cart Editor's Upsell manual rules (two buttons → modal) share `components/shared/PairingAssistant.jsx`, backed by `api.pairing-assistant.jsx` (read-only: it suggests, the page adds the picked rules to its own manual rules, and the normal Save publishes them, so the storefront is unchanged). *From past orders* = `pairing-assistant.server.js` `loadOrderPairs`: recent Shopify orders (`read_orders` = last 60 days, paged, 25 s budget) merged by order id with older webhook-recorded `store_order_line_items`, test/cancelled skipped, 5 min cache; archived/deleted products shown but can't be added. *Describe in words* (1 AI credit, only when the model is called) = the model returns a plan (`products / collections / productTypes / tags / allProducts / fromOrderHistory`) and `utils/pairing.shared.js` `buildRulesFromPlan` matches every name to the real active catalog (never invents a product; unknown names come back as warnings; "what customers buy with X" = one rule per product from past orders); no model or a failed call → `parsePromptHeuristically` ("A with B", "A -> B"). **Free reward products.** A Progress Bar tier's reward products are auto-added by the storefront drawer (`syncRewardProducts` in `cart_drawer_inline.js`, line property `_brixReward=true`). Each tier has `reward_pricing` (`progress_bar_tiers`, self-healing column, default `'regular'` so nothing already live silently becomes free): `'free'` = made free at checkout by the `extensions/brix-reward-discount` Shopify Function, `'regular'` = added at its normal price. The Function trusts only the app-owned shop metafield `$app:reward_gift_config` (built from the saved bar by `app/services/reward-gift-shopify.server.js`, never from the browser) and only discounts marked lines whose product is in that config while the cart *without gifts* meets the milestone. `syncRewardGiftDiscount` runs after AI tool saves and `api.progress-bar` saves; it never throws and returns `{verified, state, message}` (`not_needed | active | not_deployed | inactive | failed`). The drawer shows FREE only when the cart line is really at 0, and if a free-priced reward line is still charged (discount not active) it removes it and stops offering it for that page load, so a shopper is never charged for a "free gift", and the preview cart (`utils/preview-cart.js`, `PreviewCartItems.jsx`) mirrors it from the tier's `rewardPricing`. **Never claim a reward is free unless `verified`.** The Function needs `npm run deploy` and has only had its logic unit-tested (`tests/ai-handoff/reward-function.test.mjs`), not a real checkout.

### BRIX COD Checkout

Cash on Delivery orders are placed **by BRIX**; prepaid orders never touch it and keep using Shopify (or Shiprocket) checkout. Admin pages: `app/routes/app.cod.jsx` (dashboard + orders) and `app/routes/app.cod_.customize.jsx` (`/app/cod/customize?section=<id>`, laid out like the Cart Editor: sections sidebar + live preview of drawer / product page / COD checkout) (plan feature `cod_checkout`: Free = preview, Starter/Pro = live).

- **Storefront sheet:** `extensions/cart-drawer/assets/brix_cod.js` (`window.BrixCod`), loaded by the Custom Cart Drawer app embed before `cart_drawer_inline.js`. One flow (phone OTP → address → review → order) for three entry points: the cart drawer — either the BRIX drawer (`initCodButton` fills `#cc-cod-slot` next to `#cc-checkout-wrap`) or, when the BRIX drawer is off (`window.__brixCartDrawerActive` / `brix:drawer:ready`, set by `cart_drawer_inline.js`), the **theme's own drawer** (`initThemeDrawer`: finds the Checkout button inside known drawer containers, or the merchant's `drawerSelector`; a body MutationObserver re-adds it when the theme redraws; "Pay online" clicks the theme's own Checkout). Both honour `drawerPlacement` (`replace | above | below`; Replace hides Checkout only while COD is usable for the cart), `buttons.style/radius`, the fee (`codFeeEnabled`, `codFeeLabel`, `showCodFee` — hidden = still charged, folded into one "Delivery charges" line; `codFeePercent` / `codFeePercentFrom` = from that order value the fee is X% of the order instead of the fixed `codFee`, `cod.shared.js` `codFeeOf(settings, subtotal)`, mirrored by `brix_cod.js` `codFeeFor` with the same rounding, which every storefront price tag and fee line uses) and excluded tags (read from `/products/<handle>.js`; `excludedBehavior` `unavailable | hide`, also on product pages). Tested by `tests/cod/theme-drawer-browser-check.mjs`, product pages (by default takes the place of Shopify's Buy it now button and hides it, `settings.productButton.replaceBuyNow`; without Buy it now, or with that off, goes under Add to Cart; the optional `blocks/cod_button.liquid` slot overrides the spot; merchant-set margin/padding/radius in `productButton`, inline `!important` styles so theme CSS can't make it differ from the admin preview, which draws it at 80%; re-mounted by a MutationObserver when the theme redraws the form on variant change; buys only that item), and combo pages (`combo-page[.]js.jsx` renders all four layouts directly, with a COD button; only a layout it doesn't know falls back to the `preview.$templateId.jsx` iframe, whose `CdoPreviewBar` shows the button through `ComboCodContext` and posts `brix-combo-cod-open` to the parent page, which opens the sheet). "Pay online" always hands back to that surface's normal checkout, and on shops with Shiprocket on (`integrations_admin.php`) that means Shiprocket: `cart_drawer_inline.js` publishes `window.__brixShiprocket` as soon as its settings load (even with the BRIX drawer off), and `brix_cod.js` (`whenCheckoutKnown`, `themeCheckout`, `payOnlineItems`) hands the cart (theme drawer) or just the product (product page) to `BrixCheckout`, else Shopify as before; the BRIX drawer uses `ccGoToCheckout`, combo pages their own Shiprocket path. The product page payment options' Pay Online (BRIX button, Shopify's text Buy it now, the popup's "Pay online") goes to Shopify checkout, where the prepaid Function runs; on Shiprocket shops it goes to Shiprocket with a one-time Shopify code for the verified prepaid % (`api.cod.prepaid-code.jsx` via the `cod_checkout.php` relay, `services/prepaid-code.server.js`: single use, 2 h, a fixed amount on the items' variants, their subtotal as the minimum. Shiprocket checks a code by having Shopify price the order, which also runs the prepaid Function: so the code never combines with order discounts (else 10% + 10%) and is X% of the Shopify prices + one paisa, so Shopify keeps the code over the Function (on a tie it kept the Function and Shiprocket said "Please enter a valid coupon code!"); below the Function's minimum = no code; code request fails = Shopify checkout). The cart drawers' Checkout on Shiprocket shops does the same for the whole cart when Shopify shows the prepaid discount in it (`brix_cod.js` `prepaidCartCode`, paid lines only; used by `cart_drawer_inline.js` `ccGoToCheckout` unless the shopper applied a drawer coupon, and by `themeCheckout`). Shiprocket also offers its own COD, and a code can't be limited by payment method, so a shopper there could keep the code on COD. Not yet tried on a store.
- **On/off and button design per place:** `settings.surfaces.{drawer,product,combo}` are independent (turning the drawer off never affects product/combo pages or the popup). Each place has its own button look: `settings.buttons` top-level = cart drawer (`style, bg, color, radius, fontSize, bold, uppercase, icon`, texts `drawerText/productText/comboText`), `buttons.product` / `buttons.combo` = own look or `same: true` (follow the drawer; product default same, combo default = the old white-outline combo look). COD orders can never get it: `cod.server.js` puts `_brixCod=true` on the draft and every line (`COD_MARKER`, shopper-sent `_brix*` keys are dropped) and the Function returns nothing for any cart/line carrying it. ### Combo Forge Bundle Builder

The bundle builder spans **two route files** and a shared component:

#### Dashboard — `app/routes/app.bundles._index.jsx`
The dashboard loader reads `combo_templates` from SQLite via `prisma.$queryRawUnsafe` and passes `templates`, `templateCount`, `publishedCount`, and `discounts` to the page. The **action** in this same file handles two intents submitted from `TemplateManager`:
- `intent: delete` — deletes by id
- `intent: toggle_active` — sets `is_active` on the template

`TemplateManager` (`app/components/bundles/TemplateManager.jsx`) is rendered inside the dashboard and uses `useFetcher` to POST to `/app/bundles` (the `_index` route). The **"Full Library"** table shows `paginatedTemplates` — a filtered/paginated slice of `templates` from loader data. If templates aren't appearing, the issue is usually the `isClient` guard (`useState(false)` / `useEffect → setIsClient(true)`) that prevents SSR hydration flashes, or the `deletedIds` ref optimistic-removal filter.

#### Builder — `app/routes/app.bundles.customize.jsx`
A 7200+ line route that is the builder for combo/bundle pages. Key internals:
- `DEFAULT_COMBO_CONFIG` — all builder config defaults (search this object first when a config key is missing).
- `ProductCardItem` — renders each product card in the preview. Variants show when `hasVariants` (`product.variants.length > 1`). Quantity selector shows when `config.show_quantity_selector !== false`.
- Layout types: `layout1` (Guided Architect), `layout2` (Velocity Stream / tab-switcher), `layout4` (Editorial Split), `layout5` (The Weight Box), `layout6` (Quick Shop). Mapped from Shopify block names via `LAYOUT_MAP`.
- Templates are saved to SQLite via `prisma.$queryRawUnsafe` into `combo_templates`, and to the PHP backend via `sendToPhp`.
- The builder has a **template-picker mode** (`?mode=template-picker`) that shows layout cards before entering the builder; navigating away from this sends `?templateId=<id>` to load an existing template.
- **The picker has 3 cards, all on the box design** (the Quick Shop kit): **Quantity Box** (`combo_quantity_box` → `layout7`, Starter $29), **Weight Box** (`combo_weight_box` → `layout5`, Growth $59), **Value Box** (`combo_quick_shop` → `layout6`, Growth $59; was "Quick Shop"). Each is priced by one measure (`fixedMeasureFor`: quantity / weight / value; no measure picker) and has the same options: card layout (`qs_card_layout`: `quick_add` = + on the image → stepper, `normal` = full-width Add button under the price, `qs_add_label`), progress style (`qs_top_style`), filters, bottom bar, colours. Cards show the plan + price (`getMinPlanForFeature`) and "Upgrade to <plan>". An older Quick Shop saved by quantity/weight opens as a Value Box with the Value preset tiers (`asValueBox`, toast, marked unsaved; the save API forces `measure: 'value'`); until re-saved it keeps selling as before. The older designs (Guided Architect / Velocity Stream / Editorial Split, layout1/2/4) left the picker; existing ones still open, with the Design switch (`components/customization/DesignSection.jsx`, `utils/combo-design.shared.js` `switchComboDesign`) and their Single coupon / tiered progress bar Offer.

Sidebar sections for the builder live in `app/components/customization/`. The coupon/discount panel is `OfferSection.jsx` (rendered by `AdvancedSection.jsx`; section key stays `discount` for the setup tour).

#### Box pricing by weight, quantity or value (Pro, `combo_weight_pricing`)
A combo's `customization_data.pricing_mode` is `'count'` (classic: item count + optional coupon code; absent = count) or `'weight'` (the name predates measures: it means "priced by box tiers"). `weight_pricing.measure` says what the box is measured by: `'weight'` (absent = weight; total Shopify variant weight, `inventoryItem.measurement.weight`, variants without a weight don't count), `'quantity'` (number of items) or `'value'` (box subtotal; thresholds in the shop currency, no max, no box price). A tier's threshold is always `min_grams` (grams / items / amount by measure) and `max_grams` is the max weight or max items. Each box template has one measure (`fixedMeasureFor`: Quantity Box = quantity, Weight Box = weight, Value Box = value), forced by `api.bundle-templates.jsx`; only the older layout1/2/4 designs let the merchant choose. Weight boxes never carry a `measure` key, so their hash and Function config are byte-for-byte what they were before measures existed (pinned in `tests/combo-weight/measures.test.mjs`). `weight_pricing` = `{ unit, max_grams, qualify: { mode: 'layout_collections' | 'selected', collection_ids, product_ids }, tiers: [{ id, min_grams, type: 'percentage' | 'fixed_amount' | 'fixed_price', value, label }], messages, hash }`; a fixed box price needs `max_grams`, and the page blocks adding past it.
- **One copy of the rules:** `app/utils/combo-weight.shared.js` `createComboWeightCore()` (no imports, ES5 only — its source text is injected into the storefront script). The checkout Function, BRIX COD, the storefront, the preview route and the builder all price with it. `normalizeWeightPricing` validates (the builder blocks save; `api.bundle-templates.jsx` re-normalizes server-side and returns 403 `upgradeRequired` off Pro).
- **Checkout:** `extensions/brix-combo-weight-discount` (PRODUCT class, `combinesWith.productDiscounts: false`) trusts only `$app:combo_weight_config` (active weight templates on Pro, built by `services/combo-weight-shopify.server.js`, 9 KB cap) plus Shopify's own weights and collection membership (input variables `$app:combo_weight_vars` on the discount = `{ collectionIds }`). Lines carry `_brix_combo_id / _brix_combo_group / _brix_combo_version`. `syncComboWeightDiscount` runs after every combo template write (save, delete, toggle, AI create, plan webhook); it never throws and returns `{verified, state, message, templates}`. The storefront offers the box price only when `getStorefrontWeightStatus` (60 s cache) says the discount is ACTIVE with that template's hash.
- **Storefront:** `combo-page[.]js.jsx` puts a weight box in the real cart (`/cart/add.js`, replacing an earlier box of the same combo) and goes to `/checkout`, never a discount code. `brix_checkout.js` keeps any cart with `_brix_combo_id` on Shopify checkout. The iframe fallback posts `brix-combo-checkout` to the parent page.
- **Shiprocket for box combos (opt-in):** Shiprocket can't run the Function, but it does accept a Shopify code it never imported (checked by hand on a store). Quick Shop / Weight Box `qs_checkout_with` (Bottom bar section, shown only when the shop has Shiprocket on, `isShiprocketEnabled`, and the button goes to checkout): `shopify` (default), `shiprocket` = the page POSTs the box to `api.combo-box-code.jsx` (public, `text/plain` so no CORS preflight, 10 per IP per 10 min, template must be active and set to `shiprocket`), which prices it with COD's `comboWeightAdjustments` (trusted config + Shopify prices/weights, never the browser) and creates a one-time `discountCodeBasicCreate` code (`services/combo-box-code.server.js`: title `BRIX-BOX-CODE <id> <code>`, usage 1, 2 h, only the box's counted variants, minimum = their subtotal, `combinesWith.productDiscounts: false` so it never stacks with the Function), then `BrixCheckout.checkoutItems` opens Shiprocket with the items + code (fallback `/cart/<v:q>?discount=<code>`); `shiprocket_own` = Shiprocket with no code (the merchant's own Shiprocket offer). No code (below the first tier, discount not live) = Shiprocket at full price; the code API failing = Shopify checkout as before. Expired box codes are deleted at most hourly per shop. Tests: `tests/combo-weight/box-code.test.mjs`, Shiprocket scenarios in `quickshop-browser-check.mjs`. Not yet tried end to end on a store: never claim a Shiprocket order gets the box price until one is placed.
- **COD:** `cod.server.js` `comboWeightAdjustments` applies the same box price as a FIXED_AMOUNT line discount on the draft order (markers stripped, `acceptAutomaticDiscounts: false` when a box applies), after checking on a bare `draftOrderCalculate` whether Shopify reads it per unit or per line (refuses COD if neither matches). Orders get tag `brix-combo-weight` and attribute `brix_combo_weight`.
- **The Weight Box template** (`layout5`, `WEIGHT_BOX_LAYOUT`; picker card `combo_weight_box`, Pro only, "Upgrade to Pro" otherwise): the **Quick Shop design, always priced by weight** (`isWeightCombo` is true for it and the save API forces `pricing_mode: 'weight'` and `measure: 'weight'`). `usesQuickShop(layout)` (core) is true for `layout5` and `layout6`: the storefront draws both with `renderLayout6`, the builder with `QuickShopPreview` and Quick Shop's sidebar sections (filters, cards, top progress, bottom bar, colours); only the measure choice in Offer is Quick Shop-only. ### AI Agent (BrixBar) — tool-calling architecture

BrixBar is a real tool-calling agent, not a keyword matcher: any request in its coverage (cart drawer design/header/announcements/progress bar/coupon slider/upsell products/FBT/countdown timer/empty cart/checkout button/custom CSS, theme matching, discounts, Combo Forge templates) gets executed directly — it does not punt to "go do this yourself in the admin."

- Client: `app/components/ai-agent/useAiAgent.js` — thin: conversation CRUD, localStorage cache, and one `sendMessage` path that POSTs to `/api/ai/chat`. The only client-side state beyond messages is `pendingConfirmTool` (`{name, args} | null`), set when the server returns `needsConfirmation: true` for a destructive action (disabling the whole cart drawer, clearing custom CSS, removing an upsell/FBT rule, deleting a discount) — a bare "no" cancels locally, anything else re-POSTs to let the server execute or reconsider.
- Server loop: `app/routes/api.ai.chat.jsx` — authenticates, consumes one AI credit per user message (`app/services/ai-credits.server.js`), then loops (capped at 6 iterations) calling `agentTurn()` and executing any tool calls the model returns via `TOOL_EXECUTORS`, feeding results back as `role: 'tool'` messages, until the model replies with plain text.
- Tool registry: `app/config/ai-tool-schemas.js` (`TOOL_REGISTRY`, ~28 tools + `isDestructiveToolCall`) — plain JSON-schema data shared between the OpenAI native-tools path and the NVIDIA prompted-JSON fallback.
- Tool executors: `app/services/ai-agent-tools.server.js` (`TOOL_EXECUTORS`) — one function per tool, calling into `app/services/cart-config-writes.server.js` (the safe merge-on-existing-row save layer shared with the manual Cart Editor's own API routes — never a hardcoded-default overwrite), `upsell-rules.server.js`, `collection-resolver.server.js`, `combo-templates.server.js`, `discounts.server.js`, `theme-detection.server.js`.
- LLM call layer: `app/services/ai-llm.server.js`'s `agentTurn()` — real OpenAI function-calling (`tools`/`tool_choice`) when `OPENAI_API_KEY` is a real `sk-...` key; a single-tool-per-turn prompted-JSON protocol when it's an `nvapi-...` NVIDIA NIM key (an 8B model isn't trusted with native multi-tool reasoning over a ~28-tool registry).
- Conversation history persisted in MySQL via `app/services/ai-agent-history.server.js` (PHP backend tables: `ai_conversations`, `ai_messages`) — unchanged by the tool-calling rework.

### Route Naming

React Router v7 file-based routing. Patterns:
- `app.*.jsx` — embedded Shopify admin pages (authenticated via `authenticate.admin`)
- `api.*.jsx` — JSON API endpoints used by the frontend fetchers
- `webhooks.*.jsx` — Shopify webhook handlers
- `*.php.jsx` — PHP-compatible endpoint proxies (e.g., `save_cart_drawer[.]php.jsx` accepts POST from the storefront extension)

### Shopify Extension

`extensions/cart-drawer/` — a Theme App Extension with Liquid blocks. The cart drawer block (`cart_drawer.liquid`) just mounts a `#cc-root` div; the entire drawer (header, announcement bar, countdown timer, progress bar, body, footer) is rendered client-side by `assets/cart_drawer_inline.js` (`renderDrawer()`), which fetches config from `/apps/cart-app/save_cart_drawer.php` — not a separate Liquid snippet per section. FBT and the coupon slider are the exception: those render as their own web components (`<ps-fbt-widget>`, coupon slider snippets) placed elsewhere on the page (e.g. near the product page's Add-to-Cart button), fetching their own config independently. Extension settings sync happens via the Shopify CLI (`npm run deploy`).

Storefront widgets (cart drawer, FBT, coupon slider) fetch their config via the **Shopify App Proxy** at `/apps/cart-app/save_*.php`. Shopify forwards these requests to the URL set in `[app_proxy].url` in `shopify.app.toml`. If widgets show nothing on the storefront, the proxy URL is the first thing to check.

### PHP Backend

`php_backend/` contains the server-side PHP scripts deployed at `https://int.thecomboforge.com`. They own:
- `save_cart_drawer.php` — writes to the legacy `cart_drawer` MySQL table
- `save_coupon_slider_widget.php`, `save_fbt_widget.php` — widget config read by the storefront via app proxy
- `analytics.php`, `orders.php`, `clicks.php` — analytics aggregation
- `combo_save.php`, `combo_pages.php` — Combo Forge template persistence
- `ai_conversations.php`, `ai_messages.php` — AI chat history

`app/utils/api-helpers.js` is the Node.js client for all PHP endpoints. `BASE_PHP_URL` is set there. The `X-Forge-Secret` header (set to `SHOPIFY_API_KEY`) authenticates Node → PHP calls.
